# SSH 密钥生成与配置

本文说明如何为 LANDrop 生成 SSH 密钥、在自己机器上验证通过，再把公钥交给伙伴用于真实传输。

## 为什么必须用密钥

LANDrop 支持两种认证：密码和密钥。本文针对的这台机器（用户名 `ASUS`）**只能用密钥**，原因是账号类型：

```
Name   PrincipalSource       PasswordLastSet
ASUS   MicrosoftAccount      2023/9/4
```

用微软账号登录的 Windows，密码不在本地 SAM 数据库里，而 SSH 的密码认证要校验本地 NTLM 哈希——本地那份是占位符，所以无论输什么密码都会认证失败。这不是配置错误，是机制限制。

另外 `ASUS` 属于管理员组，Windows OpenSSH 对管理员组使用**特殊的授权文件路径**，不是常见的 `~/.ssh/authorized_keys`。这是最容易配错的地方，下文会专门说明。

## 一个关键限制：私钥不能设口令

LANDrop 的传输代码只把私钥路径传给 Paramiko，没有传 `passphrase`：

```python
connect_args["key_filename"] = str(Path(private_key_path).expanduser())
```

实测带口令的私钥会直接抛 `PasswordRequiredException`：

```
ed25519 无口令 -> Paramiko 可加载
ed25519 有口令 -> 失败: PasswordRequiredException
```

所以**必须用空口令生成**（`-N ""`）。代价是私钥文件本身没有额外保护，只能靠文件权限和磁盘加密保障安全。私钥泄露等同于密码泄露。

## 一、生成密钥对

在**你自己**的电脑上操作（不是伙伴的）。用 Git Bash 或 PowerShell：

```bash
ssh-keygen -t ed25519 -f ~/.ssh/landrop_ed25519 -N "" -C "landrop@ASUS-$(date +%Y%m%d)"
```

参数说明：

| 参数 | 含义 |
|---|---|
| `-t ed25519` | 密钥类型。比 RSA 更短更快，现代 OpenSSH 默认推荐 |
| `-f ~/.ssh/landrop_ed25519` | 私钥保存路径。**文件名固定用这个**，后面步骤都按它写 |
| `-N ""` | 空口令。LANDrop 不支持带口令私钥，必须留空 |
| `-C "landrop@..."` | 注释，只用于人眼识别，出现在公钥末尾 |

生成后目录里会有两个文件：

```
~/.ssh/landrop_ed25519        # 私钥：绝不外传
~/.ssh/landrop_ed25519.pub    # 公钥：可以随便给别人
```

本次生成的实际结果：

```
私钥: C:\Users\ASUS\.ssh\landrop_ed25519
公钥: C:\Users\ASUS\.ssh\landrop_ed25519.pub

公钥内容:
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIGxaP6ehDX/ZqhOG9x+AKrXVG7ankIopqxnPN8/NnHcW landrop@ASUS-20261025

公钥指纹:
SHA256:SVRUVJgXJGBXGCCkiDY9RUyH80g55H6kMBGF98MM0DU
```

> 私钥和公钥是配对的。公钥指纹（`SVRUVJ...`）用于确认"给出去的公钥是哪个"，与**服务端主机指纹**（服务器的身份，`x2Brph...`）是两个完全不同的东西，不要混淆。

## 二、收紧私钥文件权限

Windows 上私钥如果其他账户可读，OpenSSH 会拒绝使用。默认权限下 SYSTEM 和 Administrators 有完全控制权，需要改成只有你本人。

用 PowerShell（管理员也可以，但不需要）：

```powershell
$key = Join-Path $env:USERPROFILE '.ssh\landrop_ed25519'
$acl = New-Object System.Security.AccessControl.FileSecurity
$acl.SetAccessRuleProtection($true, $false)   # 关闭继承，清掉继承来的条目
$me  = [System.Security.Principal.WindowsIdentity]::GetCurrent().Name
$acl.AddAccessRule((New-Object System.Security.AccessControl.FileSystemAccessRule(
    $me, 'FullControl', 'Allow')))
Set-Acl -Path $key -AclObject $acl

# 确认只剩你一个
(Get-Acl $key).Access | ForEach-Object { $_.IdentityReference.ToString() + '  ' + $_.FileSystemRights }
```

设置后应只剩一行：

```
PIPERAS-LAPTOP\ASUS  FullControl
```

> 不要用 `icacls ... /grant:r "$env:USERNAME:(R)"` 这种写法。在 Git Bash 里 `(R)` 会被 shell 当成语法吃掉，报"无效参数"。用上面的 .NET ACL API 更可靠。

## 三、在自己机器上自测（强烈建议）

你机器上已装 OpenSSH Server，可以先拿 `127.0.0.1` 当靶子跑通全流程，不必麻烦伙伴。所有"指纹对不对""路径怎么写""权限怎么配"的问题都在自己机器上解决掉。

### 3.1 启动 sshd

以**管理员**身份打开 PowerShell：

```powershell
Set-Service -Name sshd -StartupType Automatic
Start-Service sshd
Get-Service sshd          # 应显示 Running / Automatic
```

确认 22 端口在监听：

```powershell
netstat -ano | findstr ":22 "
```

首次启动时 sshd 会自动在 `C:\ProgramData\ssh` 下生成主机密钥（`ssh_host_ed25519_key` 等）。如果这个目录之前是空的，启动后就会有内容——这是正常现象，不是错误。

### 3.2 安装公钥（管理员账号的特殊路径）

**这一步是最大的坑。** 普通账号放 `~/.ssh/authorized_keys`，但 `ASUS` 在管理员组，Windows OpenSSH 默认配置里有一段：

```
Match Group administrators
       AuthorizedKeysFile __PROGRAMDATA__/ssh/administrators_authorized_keys
```

所以公钥必须写到 `C:\ProgramData\ssh\administrators_authorized_keys`。写到 `~/.ssh/authorized_keys` 是无效的，会一直认证失败且没有明确提示。

用**管理员** PowerShell：

```powershell
$authFile = 'C:\ProgramData\ssh\administrators_authorized_keys'
$pubKey = (Get-Content (Join-Path $env:USERPROFILE '.ssh\landrop_ed25519.pub') -Raw).Trim()

if (-not (Test-Path $authFile)) { New-Item -ItemType File -Path $authFile -Force | Out-Null }
Add-Content -Path $authFile -Value $pubKey -Encoding ascii

# 这个文件的权限要求很严：只能由 Administrators 和 SYSTEM 控制
$acl = New-Object System.Security.AccessControl.FileSecurity
$acl.SetAccessRuleProtection($true, $false)
$acl.AddAccessRule((New-Object System.Security.AccessControl.FileSystemAccessRule(
    'BUILTIN\Administrators', 'FullControl', 'Allow')))
$acl.AddAccessRule((New-Object System.Security.AccessControl.FileSystemAccessRule(
    'NT AUTHORITY\SYSTEM', 'FullControl', 'Allow')))
Set-Acl -Path $authFile -AclObject $acl
```

正确的 ACL 应该是：

```
NT AUTHORITY\SYSTEM    FullControl
BUILTIN\Administrators FullControl
```

> **shell 编码坑**：在 Git Bash 里用 heredoc 写含中文的 `.ps1` 再用 `powershell -File` 执行，Windows PowerShell 5.1 会按 GBK 解析 UTF-8 文件，报"字符串缺少终止符"。脚本里只写英文，或改用 `-Command` 直接传。

### 3.3 验证密钥登录

```bash
ssh -i ~/.ssh/landrop_ed25519 -o StrictHostKeyChecking=accept-new -o BatchMode=yes ASUS@127.0.0.1 "echo KEY_LOGIN_OK && whoami"
```

`BatchMode=yes` 强制禁用密码回退——如果它成功了，说明**纯粹靠密钥**登录成功。

应输出：

```
KEY_LOGIN_OK
piperas-laptop\asus
```

> 远端默认 shell 是 cmd，串联命令用 `&&`。写成 `;` 只会把整串原样打印出来，看着像成功但 `whoami` 其实没执行。

首次连接会有一行 `Permanently added '127.0.0.1' (ED25519) to the list of known hosts.`，这是正常的。

### 3.4 在本机用 LANDrop 跑一次真实传输

启动 `F:\LANDrop\landrop-desktop.exe`，配置：

| 字段 | 值 |
|---|---|
| 远端主机 | `127.0.0.1` |
| 端口 | `22` |
| 用户名 | `ASUS` |
| 目标目录 | `C:/Users/ASUS/Downloads/LANDropTest` |
| 认证方式 | 私钥 |
| 私钥路径 | `C:\Users\ASUS\.ssh\landrop_ed25519` |

目标目录要**先手动创建**，LANDrop 不会自动建。路径用正斜杠 `/`，即使目标是 Windows。

点「检查主机指纹」，界面会显示类似：

```
ssh-ed25519 SHA256:x2Brph/7uQ8yAWsMqLjQ0LhhFgSHQvu0n1saQyjogAg
```

核对方法，在本机跑：

```powershell
ssh-keygen -lf C:\ProgramData\ssh\ssh_host_ed25519_key.pub
```

一致就点「确认并保存」，然后选文件发送。

本次已用 LANDrop 的实际传输代码验证过一遍，结果：

```
RESULT: C:/Users/ASUS/Downloads/LANDropTest/keytest.bin
sha256: 6246dce283e54bb2bb0cb3ad5caedc5a31139ccf6a7c36230b6ad7c0e6825e35
remote exists: True
bytes match: True
```

## 四、把公钥交给伙伴

自测通过后，把**公钥**（`.pub` 文件，不是私钥）发给伙伴。两种方式：

**方式 A：直接发文本。** 打开 `C:\Users\ASUS\.ssh\landrop_ed25519.pub`，把这一整行发给他：

```
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIGxaP6ehDX/ZqhOG9x+AKrXVG7ankIopqxnPN8/NnHcW landrop@ASUS-20261025
```

**方式 B：发文件。** 直接把 `landrop_ed25519.pub` 发过去。

**绝对不要发 `landrop_ed25519`（没有 .pub 后缀的那个）。** 那是私钥，泄露后任何人都能以你的身份登录伙伴的机器。

## 五、伙伴那边怎么装公钥

### 5.1 伙伴是 Linux / macOS

```bash
# 把收到的公钥追加到授权文件
mkdir -p ~/.ssh && chmod 700 ~/.ssh
cat >> ~/.ssh/authorized_keys <<'EOF'
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIGxaP6ehDX/ZqhOG9x+AKrXVG7ankIopqxnPN8/NnHcW landrop@ASUS-20261025
EOF
chmod 600 ~/.ssh/authorized_keys
```

权限不对是最常见失败原因，务必执行 `chmod`。

### 5.2 伙伴是 Windows（普通账号）

管理员 PowerShell，把上面那行替换进命令：

```powershell
$pubKey = 'ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIGxaP6ehDX/ZqhOG9x+AKrXVG7ankIopqxnPN8/NnHcW landrop@ASUS-20261025'
$authFile = Join-Path $env:USERPROFILE '.ssh\authorized_keys'
New-Item -ItemType Directory -Path (Split-Path $authFile) -Force | Out-Null
Add-Content -Path $authFile -Value $pubKey -Encoding ascii
```

### 5.3 伙伴是 Windows（管理员账号）

同第三节 3.2，写到 `C:\ProgramData\ssh\administrators_authorized_keys` 并设置上述 ACL。

### 5.4 伙伴确认 sshd 允许公钥认证

打开 `C:\ProgramData\ssh\sshd_config` 确认这两行没有被设成 `no`：

```
PubkeyAuthentication yes
#PasswordAuthentication yes
```

改过配置需要重启服务：

```powershell
Restart-Service sshd
```

## 六、连伙伴时的配置

| 字段 | 值 |
|---|---|
| 远端主机 | 伙伴的**局域网 IP**（不是 `127.0.0.1`） |
| 端口 | 通常 `22` |
| 用户名 | 伙伴的 Windows 登录名 |
| 目标目录 | 伙伴那边**已存在**且有写权限的目录，如 `C:/Users/伙伴名/Downloads` |
| 认证方式 | 私钥 |
| 私钥路径 | `C:\Users\ASUS\.ssh\landrop_ed25519` |

指纹核对要用伙伴机器上的命令：

```powershell
# 伙伴 Windows 上跑
ssh-keygen -lf C:\ProgramData\ssh\ssh_host_ed25519_key.pub
```

两边显示的 `SHA256:...` 完全一致才能点「确认并保存」。不一致就停下——可能是连错机器，或网络中间有人。

## 七、排查对照表

| 现象 | 原因 | 处理 |
|---|---|---|
| `Permission denied (publickey)` | 公钥没装到正确文件 | 管理员账号必须用 `administrators_authorized_keys`，见 3.2 |
| 同上，且公钥确认已写入 | 文件 ACL 不对 | 按 3.2 设置，只能有 Administrators 和 SYSTEM |
| 同上，Linux 伙伴 | `authorized_keys` 权限过宽 | `chmod 600 ~/.ssh/authorized_keys`、`chmod 700 ~/.ssh` |
| `Load key: invalid format` | 路径指向了 `.pub` 文件 | 填**没有** `.pub` 的那个 |
| `PasswordRequiredException` | 私钥带了口令 | 用 `-N ""` 重新生成 |
| `UNPROTECTED PRIVATE KEY FILE` | 私钥权限过宽 | 按第二节收紧 |
| 提示 `Connection refused` | 伙伴 sshd 没启动 | 伙伴执行 `Get-Service sshd` |
| `Connection timed out` | 网络不通或防火墙 | 先 `ping 伙伴IP`，再查防火墙入站规则 |
| 认证成功但传不动 | 目标目录不存在或不可写 | 让伙伴先建目录并确认权限 |

## 八、安全提醒

- 私钥 `landrop_ed25519` 等同于你的登录凭据，**不要放进网盘、聊天记录、代码仓库**。
- 因为它没有口令，一旦被复制就能直接使用。建议开启 BitLocker，或在共享电脑上用完删掉。
- 公钥 `landrop_ed25519.pub` 可以自由分发，泄露无风险。
- 如果怀疑私钥泄露：重新执行第一步生成新密钥，把新公钥重新发给伙伴，并在伙伴机器的授权文件里删掉旧的那行。
- LANDrop 保存的主机指纹在 `%APPDATA%\LANDrop\known_hosts`，与系统 `~/.ssh/known_hosts` 是分开的。删掉这个文件会要求重新确认主机身份。
